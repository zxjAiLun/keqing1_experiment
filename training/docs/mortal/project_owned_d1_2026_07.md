# Project-Owned D1 Data Lineage (2026-07)

## Scope

D1 is the next single-variable data experiment after closing the
`legal_mean_mc` objective branch. It asks whether a replay pool generated by
the project-owned 70k lineage can produce a stronger continuation than the
current M0 corpus. It does not change the reward, objective, optimizer,
network, learning rate, CQL, or training length.

This document is a pre-registration plan. No D1 data generation or training
is started by this document.

## Fixed Training Contract

Both arms use:

- 70k weights plus the identical 70k Adam state;
- fresh scheduler, scaler, RNG, and data stream;
- `reward.mode = final_rank_mc`;
- `objective.mode = behavior_action_mc`;
- existing DQN/CQL/next-rank/Aux implementation;
- 70,000 -> 72,000 steps;
- three matched training seeds, to be recorded in the run manifest before training;
- Windows CUDA, `num_workers=0`.

The control is the existing M0 corpus under
`artifacts/experiments/model_pool_2026_07/V2_data/`, using its existing
training-view filter. The variant is one new D1 corpus with the same target
number of hanchans and a single project-owned training perspective per
hanchan.

## D1 Generation Contract

Generate exactly 6,000 independent hanchans with
`training/mortal/four_player_native.py` and the native B250 protocol:

| Seat population label | Checkpoint | Role |
| --- | --- | --- |
| `K0_70k` | 70k promoted candidate | trainable project-owned perspective |
| `ext_mortal` | external Mortal checkpoint | external reference style |
| `V3_74000` | project V3 step 74,000 | frozen project continuation style |
| `V2_74000` | project V2 step 74,000 Mortal checkpoint | frozen alternative project style |

Use random seats, one log per seed, `seed_key=8192`, B250 generation, CUDA
required, AMP disabled, and rank points `[90,45,0,-135]`. The registered
generation seed range is `1600000-1605999`; it must not overlap any existing
pool. Only the `K0_70k` player name is admitted to the D1 training view. The
other three models are environment opponents and are not learned into the
training target. The project-owned `keqing_grp_v1` checkpoint is a final-rank
predictor rather than a playable Mortal policy, so it remains an analysis
model and is not placed in this arena.

The data audit must report:

- 6,000 files and 6,000 canonical unique hanchans;
- zero malformed logs and zero seed/key overlap;
- exactly one `K0_70k` training perspective per hanchan;
- rank, agari, houjuu, fuuro, and riichi distributions for the trainable view;
- full model SHA256 values, generator commit, Rust/libriichi revision, and
  B250 protocol metadata.

## Matched A/B Evaluation

For each matched training seed, train M0 and D1 from the same parent and
evaluate the resulting checkpoints in one B250 random-seat lineup:

```text
70k / ext_mortal / M0_control / D1_project_owned
```

Use 1,000 hanchans per training seed and separate evaluation seed ranges.
The primary quantity is the complete-hanchan paired `D1-M0` Pt difference;
also report `D1-70k` and `M0-70k`. Use pooled hanchan bootstrap and
equal-seed hierarchical bootstrap. Do not use 1v3/3v1 or a two-way aggregate
as the primary decision.

## Decision Rules

- Promote D1 as the project-owned data lineage only if the seed-level `D1-M0`
  effect is stable and the hierarchical interval supports a positive effect;
  no single checkpoint is promoted from one favorable seed.
- If D1 improves over M0 but both remain below 70k, record it as a data-route
  improvement without claiming K1.
- If D1 is neutral or worse, close this population recipe and inspect replay
  coverage, trainable-view action distribution, and state diversity before
  changing any objective or optimizer variable.
- Do not regenerate a new pool after each archive step. One D1 pool is reused
  for the complete matched A/B.
