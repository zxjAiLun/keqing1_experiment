## 4. 随机抽样具体发生在哪里

准备脚本先按路径排序全部 `.mjson`，默认无 limit；随后用 `seed=20260428` 打乱路径，5% 作验证集，其余作训练集；压缩只改变容器格式，不重写内容。

用历史函数在 105765 个合成路径上做纯逻辑验证，得到 train=100477、val=5288。这是“按历史总数和默认参数推算”，不是重新盘点了原始 105765 个文件，也不能代替当时的 manifest。

训练时，上游 `0cff2b5:mortal/dataloader.py` 再打乱文件顺序和缓冲区内的决策行。因此：划分训练/验证是本地准备脚本完成，训练行的 shuffle 使用上游 loader；不是简单地“上游随机抽一小批牌谱”。如果实际曾使用准备脚本的 `--limit`，其实现是先取排序路径的前 N 项再分割，而非随机选 N 项；没有找到证据表明当时使用过它。

## 5. 两个明确的历史实现特征，以及一个待核验的数据风险

### 5.1 采集高手的历史牌谱，不等于只训练高手视角

现存 K0 配置的 `player_names_files=[]`。旧 runner 将空玩家名单传给上游加载器；`0cff2b5:libriichi/src/dataset/gameplay.rs` 在名单和排除表为空时保留全部四名玩家。

因此按该配置执行，会学习四家决策，不是只学习被检索的那位玩家。其余三家也可能很强，不能武断称为低质量，但训练样本的身份定义与“高手专属动作”不同。

### 5.2 早期续训恢复参数状态，不恢复数据游标

旧 runner 每次启动执行 `random.seed(seed)` 和 `torch.manual_seed(seed)`，默认 seed 固定；存在 checkpoint 时恢复 Brain/DQN/Aux、optimizer、scheduler、scaler、steps，然后重新创建 DataLoader。checkpoint 没有数据游标或 RNG 状态，代码没有按已完成 steps 跳过已消费行。

因此在 seed、文件索引、运行实现和 worker 设置等相同的条件下，分段重启会重新读取同一打乱序列的前段；它不是严格连续的数据流。不同单次运行长度会影响哪些数据被反复看见、哪些尚未覆盖。

这与用户所说的分次启动续训相关，但没有完整启动记录，不能计算实际重复次数，也不能断言这就是 80K 放铳升高的原因。这里并没有发现“续训丢失 Adam”的证据；相反，旧代码明确恢复 optimizer。

### 5.3 旧切分按路径，不按 canonical game ID

准备脚本没有在划分前做跨目录 log-ID 或内容去重。若同一场牌谱出现在不同玩家历史目录中，存在重复或跨 split 的可能。

这是实现层面的风险，不是已经在旧语料中发现了泄漏；原始文件不在眼前，不能报重复率。新基线需要按牌局身份去重后再划分，不能机械照搬旧准备脚本。

## 6. 70K 留下来的原因，与用户记忆吻合

历史 500h 同模型自对弈统计（不是本次重跑）：

| 指标 | 70K | 80K |
| --- | ---: | ---: |
| 和牌率 | 21.69% | 22.28% |
| 放铳率 | 13.13% | 14.66% |
| 副露率 | 28.71% | 31.82% |

80K 相对 70K 副露更多、放铳更多，且历史双向 gate 未支持替换 70K。用户以最终对战数据为主、人工复盘辅助抽查的做法合理；无需逐局人工验收几千份牌谱。

但不把和牌/放铳率当作越低或越高越好的一维目标；最终还是预注册的 Pt、平均顺位及不确定性。70K 作为成功门槛之一，external 作为更高参照；赢 70K 不自动等于达到 external 水平。

本次找到的 100K 文本属于未来可能续训与停止提醒，没有定位到确认完成 100K 的记录或文件，不能确认它曾训成。
