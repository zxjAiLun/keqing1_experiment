# P4-M11：direct PG 学习预算、K0 实用门与 external EVE 门

日期：2026-09-13。负责人方向决定与本地执行交接。修订：两级目标对齐；训练配方与训练预算不变，external 从条件差距测量升级为正式 Gate B。

## 1. 目标与当前事实

本轮研究问题：给已运行的 direct-PG 闭环一次明显更充分的连续学习机会，判断 project-owned 模型能否先超过 K0_70k 的历史普通训练水位，再挑战 external_mortal 所代表的目标 EVE 强度区域。战胜 K0 是第一道实用门，不是项目研究成功的终点。

| 对象 | 固定角色与口径 | 不能声称 |
| --- | --- | --- |
| K0_70k | 历史 conventional-training reference / 当前消费参考；人类牌谱与常规 Mortal 训练路线的 observed high-water mark | 已证明的训练范式天花板、战胜它即完成 EVE 目标 |
| external_mortal | strong external reference / EVE gate proxy；可实际对战的目标强度参考，同时也是本轮固定训练对手 | 对整个 EVE 生态的通用等级认证 |
| Mortal 3.0 | 用户的体感参照 | 没有权重和直接对战证据，不建立与 external 的已验证等级对应 |

截至本计划：K0 是唯一正式 play/review 消费参考；hard50k 对 K0 未检出明确差异，C4 没有直接对 K0 的替代验收。P4-M10 not_supported 及所有旧实验停止规则保持原样，不能称已有 >K0 模型。文档不再把 K0 简称为 baseline；下文 baseline=0 专指策略梯度的回报基线，不是模型角色。

本轮只有 `hard50k → C4 → U32` 一条 lineage。即使两个门都通过，也只说明这条训练过程产出了达到目标的 checkpoint，并强力支持继续投入该路线；不孤立证明数据量、配方、机制或随机性各自的贡献，不证明稳定可复现地胜出。独立训练重复留待出现值得复现的结果后再决策，本轮不启动多 seed 训练。

P4-M11 是新的单候选学习预算，不是重开 P4-M10，不修改旧训练身份、旧预算或旧结论。用户已认可继续 direct PG，由负责人主动定方案，本地 agent 实现与执行，云端做聚焦代码 review，负责人在结果完成或实质 blocker 时接手。不需要每个正常阶段重新请示。

## 2. 路线决定及预算依据

从 P4-M10 的固定末端 C4 继续，而非挑选 C1-C3，不重新跑 hard50k 到 C4。

只增加学习周期，保留已运行的目标、模型、采样与优化器配方。理由是闭环可用、实际策略已有小幅移动、没有崩溃证据；并非小位移证明延长必然有效。此次投入检验更大预算的端点能否满足实际替代目标，不声称辨明所有机制或保证收敛。

- 新增 32 cycles，每轮 64 seed × 四座轮换 = 256 半庄。
- 新增 8,192 半庄、32 次 optimizer update；全谱系累计 36 次 PG update。
- 只评新实验 U32 末端。U08/U16/U24 不做实战，不按 telemetry 选点。
- 不在 U08/U16 再设置负责人批准门；正常且安全则自动完成 U32。
- 预算来自已测四轮 1,886.9 秒：32 轮线性外推约 4.2 小时；计划训练 4–5 小时。Gate A 评测2,048半庄；仅Gate A通过后追加已预定的Gate B评测2,048半庄，评测合计上限4,096半庄。依历史吞吐估计：只运行Gate A的全流程约6–7小时；两门及工程检查全流程约7–9小时。后者是此次新增的条件预算，不是训练预算增加，性能变化可能使估计失准。
- 自动运行时间上限：训练相关活跃运行累计 6 小时；超过则安全暂停，不把部分端点当 U32，不擅自增加预算或宣布失败。硬件/实现中断不是科学负结果。

## 6. Sequential two-gate evaluation：固定 U32，不更换权重

### Gate A — K0 practical replacement gate

历史训练/当前消费参考：`artifacts/mortal_training/checkpoints/mortal_default_70k_promoted_candidate.pth`。

- solo方向：U32 单挑 vs 3×K0，1,024半庄。
- mirror方向：K0 单挑 vs 3×U32，1,024半庄。

### 两个门共用的单门 primary endpoint（单位一致，逐门独立裁决）

对该门的参考模型R和每个seed i：S_i是四次轮换中的U32单挑平均rank pt；O_i是R单挑平均rank pt。Gate A中R=K0，Gate B中R=external。

统一为每个候选座位单位：镜像候选收益为 `-O_i/3`。预先定义对两种桌面组成等权的协议指标：

`G_i = (S_i - O_i/3)/2`。

每个门对自己的256个seed块同时重采样两方向（保留配对），5,000次bootstrap，统计seed固定20260913，报告mean(G)及双侧95% percentile CI；同时分别报告S、O原单位、-O/3及各方向CI。两门不混合seed、不拼接成一个总体CI。不能将其叫通用Elo或任意对手下的强度。

单门PASS需要同时满足：

1. mean(S)>0 且 mean(-O/3)>0；
2. G 的95% CI下界>0；
3. mean(G)>=+2.0 rank pt/候选座位/半庄。

第3项是预设实用收益阈值，两门一致；不是基于本轮结果选择的数字。该协议是针对指定参考对手的筛查，不证明所有阵容下均优于R，也不孤立归因PG相对C4/hard50k的因果增益。本轮不新增parent对照以追求机制归因。Gate A、Gate B按预定顺序执行，不能因不满意某一门结果改变指标、阈值或样本数。

Gate A条件未满足：`practical_gate=not_supported`，`eve_gate=not_run`。本轮没有交付被证据支持为强于历史普通训练参考的模型；不替代K0，不运行Gate B，不挑中间checkpoint、不追加seed、不自动调参/续训。不能写成已证明U32不强于K0或PG理论失败。

## 10. 执行层缺陷修复（2026-09-13，聚焦 review REJECT 后；训练仍未启动）

云端聚焦 review **REJECT** 了 §9 的启动前实现，裁定**训练方向不变**，但存在四类**执行层**缺陷（不是算法问题、不是重新选路），并要求补负向测试。本节登记修复：**不改训练算法、不改冻结配方、不重新建平台**。明确保留不动：C4 权重 + Adam 恢复、每轮全批累积后单步更新、checkpoint + 完成标记结构。

### 10.1 缺陷一：资源保护只在 cycle 前后生效

review 认定：`sample_interval_seconds=30` 只是配置；快照实际只在 cycle 前后各取一次，`guard.observe()` 只作用于 cycle 前那一次，而单 cycle 长达数分钟（in-process 采集可以接受，丢掉 in-flight 监控不可以）。且 `preflight_violations({})` 在监控字段全缺时返回 `[]` —— 即「探针读不到」被当作「资源检查通过」。

修复：

1. 新增 `ResourceWatchdog`：守护线程按 `sample_interval_seconds` 在 cycle **运行期间**持续采样，每个样本立即落盘到 `resource_samples.jsonl`，并折叠进安全暂停／硬停状态机（沿用「连续两次」规则）。
2. `REQUIRED_RUNTIME_METRICS`（有 GPU 时为 `REQUIRED_RUNTIME_METRICS_WITH_GPU`）：**关键指标缺失即视为违约**，不再默认通过；`preflight_violations({})` 现在非空。
3. 分级收敛：`critical_violations` **只对读得到的、低于硬停阈值的值**生效（`os._exit(PAUSE_EXIT_CODE)`，同时写 marker）；探针读不到只升级为安全暂停。理由：「机器要坏了」才硬停，「看不到」不足以判定机器要坏了。
4. cycle 内三处安全点（采集后、update 前、commit 前）均调用 `watchdog.check()`。

### 10.2 缺陷二：resume 不校验已保存的身份

review 认定：`load_committed_checkpoint()` 不校验 checkpoint 内记录的配方／环境／parent／cycle，并把**当前配置**的 parent SHA 塞进返回值，使调用方的 parent 比较成为空操作；CPU mock 下错误 parent、错误环境、`cycle=999` 均被接受。

修复：

1. `load_committed_checkpoint()` **只读 checkpoint 自身记录的字段**并与本进程比较：recipe、environment、lineage parent（路径 + SHA）、cycle、`completed_cycles`、Adam step；任一不符即 `P4M11ContractError`。返回值携带**记录的** parent，不再是当前配置。
2. 加载 optimizer 后校验 Adam step == `parent_inherited_adam_step + cycle`，与继承步数一致。
3. 新增 `environment_fingerprint`（interpreter / python / torch / `cuda_available` / **native 二进制 sha 集合**）与 `environment_problems`：**native 二进制集合变化即拒绝恢复** —— 正是 V1/V2/V3 三个 riichi 构建并存的风险点。路径记录但不参与比较。
4. 采集复用同步收紧：manifest 写入 challenger/champion 标签、**champion SHA 与路径**、完整采样配置、seed 段、seed key、`sampling_seed`、`splits_per_seed`、`return_baseline`、native sha、torch/interpreter；任一不同即不复用。

> 副作用（有意）：环境指纹绑定 native 二进制与 torch 版本，因此用非 mandated 解释器产出的 checkpoint **不会**被 mandated 解释器接受。§5 的解释器要求因此成为**强制**约束，而非约定。

### 10.3 缺陷三：重采会覆盖失败证据

review 认定：复用检查失败后仍在同一个 `cycle_dir` 调采集器，而冻结的采集器以 `"wb"` 打开原始观测文件，会**截断** `obs_fp32.bin`，即失败证据被下一次尝试覆盖。

修复：

1. 每次采集写入**不可变的 attempt 目录** `cycle{N}/attempt{K}/`（`next_attempt_dir()` 绝不复用已存在的 attempt）；失败尝试原样保留，新尝试落新目录。
2. 采集产物（`obs_fp32.bin`、`probe_records.jsonl`、`logs/`）与 manifest 全部写在 attempt 目录内；cycle 根目录只剩确定性的 `collection_weights.pth`（身份文件，不是失败证据）。
3. `find_reusable_attempt()` 由新到旧逐个校验 manifest；`reusable_collection()` 要求完整性与 sha 全部匹配。
4. 损坏的完成标记、缺失的 checkpoint **直接报错**，不再 `continue` 跳过（跳过会紧接着在它引用的证据上重做该轮）。
5. 所有 torch 写入统一走 `_save_torch_atomic`（临时文件 + `os.replace`）；模块内不再有裸 `torch.save`，身份文件不可能被观察到半写状态。

### 10.4 缺陷四：CLI 可绕过固定预算、把中点当完成

review 认定：`--cycles 64 --seeds-per-cycle 32` 能通过预算检查，而采集器仍按配置的 **64 seeds/cycle** 采集，实际 16,384 半庄超出授权上限；`--cycles 1` 会把 U01 报为完成并写成最终评测端点。

修复：

1. 官方入口**删除** `--cycles` 与 `--seeds-per-cycle`；每轮 seed 数**恒取冻结配置**，预算检查与采集器不可能再不一致。
2. 诊断必须显式走 `--diagnostic-cycles`，结果写 `p4m11_diagnostic_result.json`（而非 `p4m11_result.json`）；`completion_status()` 对诊断运行**永不返回 complete、永不给出评测端点**。
3. 完成锁定为 **U32 / Adam step 36 / parent 未被修改 / 非诊断**（`completion_status()` 抽为纯函数以便测试）；否则给出 `incomplete_reason` 且 `evaluation_endpoint = null`。
4. 六小时计时改为 heartbeat 记账（`begin_active_cycle`/`end_active_cycle`）：**中断的尝试也计入**。只统计写入 `cycles.jsonl` 的轮次会让崩溃循环无限跑。

## 11. 复审后三项执行缺口修复（2026-09-13 第二轮；训练仍未启动）

第二轮聚焦 review 认可 `757651c` 修复的四类（19/19 复现通过：父模型/环境校验、独立 attempt 保留旧产物、损坏完成标记拒绝恢复、U32 完成门），但另两个 CPU 边界检查复现出三个新缺口。**方向与预算不变**，不新增实验、不重做资源探针、不追加研究诊断、不调整 PG 配方。

### 11.1 缺口一：「连续两次严重压力」会累计不连续样本

`ResourceWatchdog.observe()` 只在 `critical` 为真时才把样本喂给 critical guard（`if critical and self.critical_guard.observe(critical)`），健康样本直接跳过 → **计数永不清零**。实测：严重压力 → 健康 → 严重压力 仍触发硬退出。另外，阶段边界快照与后台采样推进同一个计数器，可能把几乎同时发生的两次读数当成持续压力。

修复：

1. `observe(snapshot, *, advance=True)`：`advance=True` 时**两个 guard 都无条件喂入**，因此健康样本会真正清零严重压力计数；`advance=False` 用于阶段边界快照 —— 仍然记录并逐条落盘，但**不推进计数器**。边界样本不推进计数，但若守卫已触发，`watchdog.check()` 依旧会报。
2. `record_sample()` 一律走 `advance=False`；只有 watchdog 的定时采样计入持续压力。

### 11.2 缺口二：崩溃后的停机时间被算进六小时预算

`accumulated_active_seconds()` 用 `now − started_unix` 计算运行中周期的时间，而 heartbeat **从不周期刷新**。实测：周期开始后中断、八小时后恢复，直接报 **28,800 秒** active time —— 晚上关机、第二天续跑，会因「预算耗尽」无法继续。

修复：

1. heartbeat 新增 `elapsed_seconds`；新增 `refresh_active_cycle()`，由 in-cycle watchdog 的 `on_tick` 在**每次定时采样**时刷新（`started_unix` 不动，`elapsed_seconds` 单调不减）。
2. `accumulated_active_seconds()` 只计 `active_seconds_at_start + elapsed_seconds`（即**最后一次心跳**），**不计进程死亡后的间隔**。
3. `end_active_cycle()` 正常结束时知道进程全程存活，因此按 `now − started_unix` **足额**计入。
4. 代价：每次崩溃最多少计一个刷新间隔（默认 30 s）的真实工作量；换来的是隔夜等待零计费。中断尝试仍然收费，关机等待不收费。

### 11.3 缺口三：保存的冻结配方可能与实际运行不同

入口仍允许 `--champion`、`--grad-clip`、`--micro-batch` 等覆盖：**执行使用覆盖值，而 checkpoint 的 `recipe` 保存固定 `P4M11_CONFIG`**。且对手 SHA 只绑定在**采集 manifest**，未进入 checkpoint 恢复契约 —— 换对手会拒绝复用旧采集，却仍可能继续同一条训练 lineage。

修复：

1. 新增 `assert_recipe_arguments()`：官方入口**只在覆盖值等于批准值时**接受（`--champion`、`--challenger-label`、`--champion-label`、`--micro-batch`、`--grad-clip`），任一偏离即 `P4M11ContractError`。冻结值仍可在 CLI 中检索，授权变更只需改一处 config。
2. `P4M11_CONFIG` 新增 `champion_sha256`（冻结 external SHA）、`challenger_label`、`champion_label`；`main` 额外校验实际 champion 文件哈希等于冻结值。
3. `training_contract()` 新增 `opponent` / `opponent_sha256`；checkpoint payload 新增 `opponent_sha256`；`load_committed_checkpoint()` 读并校验**记录的**对手（payload 优先，回落到 contract），缺失或不符即拒绝恢复。

### 12.1 collection `complete=true` 必须在 authoritative logs 校验之后

旧顺序：`collect_cycle` 返回 → 写 `collection_manifest.json`（`complete: true`）→ **才**解析 arena logs → **才** `assert_collection_complete()`。于是 failure mode 是：

```
attempt1：records/obs 完整，arena logs 缺局
  → manifest 已经是 complete=true
  → assert_collection_complete FAIL
  → 重启
  → find_reusable_attempt() 认为 attempt1 可复用
  → 在同样的残缺 logs 上永远失败（永不创建 attempt2）
```

immutable attempts 保护了失败证据，但正因为如此，它会**永远复用坏 attempt**。

修复：manifest **只在** `hanchan_returns_from_logs` + `assert_collection_complete` PASS **之后**才原子写入。因此「manifest 存在」⇔「authoritative log completeness 已通过」；残缺 logs 的 attempt 干脆没有 manifest → `reusable_collection()` 返回 `None` → 不复用 → 下一次采集落在新的 attempt 目录。**不需要 provisional manifest**。

### 12.2 `.done.json` 必须是整个 cycle 的最后一步

旧顺序（均在 `train_cycle()` 内）：optimizer step → `save Ux.pth` → `write Ux.done.json` → return；而 `cycles.jsonl` 的 append+fsync 却发生在回到 `main()` 之后。于是仍可能：

```
U07.pth        存在
U07.done.json  存在
cycles.jsonl   没有 U07
```

即源码注释的「completion marker last」只表示「checkpoint 之后」，而**不是**「整个 cycle durable transaction 的最后一步」。

修复：`train_cycle()` **不再写 marker**，改为返回 `report["commit_marker"]` payload；`main()` 的顺序固定为 **append `cycles.jsonl`（flush+fsync）→ 写 `Ux.done.json`（最后）**。不引入 WAL、不新增 persistence layer。

顺手收紧 `committed_cycles()` 的 fail-close：

- `U2.done.json` 必须声明 `completed_cycles=2`（文件名与内容一致），否则报错；
- committed set 必须**从 U1 起连续**，有缺口即报错。

### 12.3 fresh start 的 device / interpreter / native 必须钉死

`--device` 默认 `cuda if available else cpu`，而 CUDA 只在显式 `--require-cuda` 时才强制。于是错误 CPU venv → `torch.cuda.is_available()==False` → 默认 cpu → 不传 `--require-cuda` → fresh U01 照常启动。环境 fingerprint 在 fresh start 只**记录**实际环境，真正的比较发生在 resume（当前环境 == 已保存环境），因此只能防「U01 对、U02 换环境」，防不了「U01 一开始就错」——本轮开发中确实发生过一次先拿错 CPU interpreter。

修复：

- 新增 `assert_pinned_device()`：**无条件**要求 `device.type == "cuda"` 且 `torch.cuda.is_available()`，不存在 CPU fallback；删除 `--require-cuda`（它已无意义，保留只会误导成「可选」）。
- 新增 `assert_fresh_start_environment()`：fresh start（`last_committed == 0`）时额外钉死 `sys.executable` == 预注册的 `keqing1/.venv-win/Scripts/python.exe`，且 native 二进制集合必须含预注册 V1 `19bb181e…`。resume 由 `load_committed_checkpoint()` 的环境比较负责。
- external SHA 已在上一轮钉住，本轮未动。

### 12.4 删除 `--diagnostic-cycles`

它虽然不会把 U01 声明成 final endpoint，但仍会在正式 output dir 产生 `U1.pth` / `U1.done.json`，而 `committed_cycles()` 无法把它与真实 U1 区分。已**整体删除**该 flag 及其全部分支（`p4m11_diagnostic_result.json`、`completion_status()` 的 `diagnostic` 参数）。现有 dry-run + 聚焦测试 + 复现检查已足够，不再保留「真跑几个 optimizer cycle 的 diagnostic mode」。
